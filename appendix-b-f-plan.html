Apêndices B–F — plano de implementação e estado verificado

Este documento é o plano executável dos Apêndices B, C, D, E e F de RustyDroid.md. A spec é um rascunho: a fonte de verdade do estado é o código, os registros em data/ e os testes. Cada afirmação de “feito” aponta para um teste ou arquivo. Nada aqui promove um status em data/*.toml; isso só acontece no PR que muda o código.

Estado de referência: origin/main após o PR #541 (1130a44), mais o PR desta rodada.

Segunda rodada de pesquisa (2026-11-06): fontes lidas e pré-requisitos

A pesquisa anterior parou no trecho de revogação de PermissionManagerServiceImpl.java. Nesta rodada o arquivo inteiro (5368 linhas, services/core/java/com/android/server/pm/permission/, branch main) e PackageManager.java foram baixados de android.googlesource.com (?format=TEXT) e lidos. Cópias locais fora do repositório: /home/user/appc/aosp/.

  • revokeWhenRequested (fonte completa do comportamento):
    • Doc da flag (PackageManager.java:5335): “The permission has not been explicitly requested by the app but has been added automatically by the system. Revoke once the app does explicitly request it.”
    • Revogação em revokePermissionsNoLongerImplicitLocked (PMSI ~2984–3045). Chamada em updatePermissions de cada pacote (~2953), com o conjunto de permissões implícitas do pacote. Revoga só se: permissão concedida e runtime; flag REVOKE_WHEN_REQUESTED setada; não está em BLOCKING_PERMISSION_FLAGS (system fixed, policy fixed, granted by default); target SDK do UID >= 23; e não é a preservação de “Nearby devices” com ACCESS_BACKGROUND_LOCATION concedida. Ao final, a flag é removida sempre; as flags do usuário só se houve revogação.
    • A flag é setada na migração de permissão split (PMSI ~3188), exceto ACTIVITY_RECOGNITION e permissões de mídia aural/visual. Herança em ~4800–4870 (merge de flags entre fontes).
    • Pré-requisito que falta no VM: não existe ciclo de update de pacote (o motor é construído uma vez em PermissionEngine::install) e não há conjunto de permissões implícitas por versão. Sem o gatilho de update, a função de revogação não teria chamador. Adicionar esse ciclo muda o comportamento de todo app com permissão split, então precisa de decisão do usuário (ver §6).
  • instant (fonte completa do comportamento no framework):
    • checkSinglePermissionInternalLocked (PMSI ~988–999): para app instantâneo, uma permissão concedida só conta se Permission.isInstant().
    • grantRuntimePermission (PMSI ~1470–1472): concessão de permissão não-instant a app instantâneo lança SecurityException (“Cannot grant non-ephemeral permission”).
    • Pré-requisito que falta no VM: não existe estado de app instantâneo. isInstantApp é fixo em false (android_pm.rs:721). Modelar o estado muda a resposta de isInstantApp para qualquer app que o VM hospede, então também precisa de decisão do usuário.
  • softRestriction (concessão, fonte parcial):
    • grantRuntimePermission (PMSI ~1378–1390 e ~1456): permissão soft restricted só é concedida se SoftRestrictedPermissionPolicy.forPermission(...).mayGrantPermission() for verdadeiro; senão a concessão é recusada (“Cannot grant soft restricted permission”). A própria política (services/core/java/com/android/server/policy/SoftRestrictedPermissionPolicy.java) ainda não foi lida.
    • O VM não tem nenhuma modelagem de soft restriction (rd-framework/src/fd_permissions.rs). A forma fraca continua na pergunta §6 item 2a.

A flag role foi implementada: a documentação AOSP de roles diz que o role concede as permissões declaradas em <permissions> ao holder. A ligação SMS → permissões de SMS vem da política do Play (grupo SMS exige default SMS handler). A regra “holder do role dispensa hardRestricted” é uma decisão de modelagem deste projeto, não um fato da documentação do Android; está marcada no código.

Lacuna conhecida de teste

A resposta de shouldShowRequestPermissionRationale no VM não tem teste de ponta. Tentativa com m10::call_instance em receptor Context retornou None (a intrínseca não casou o receptor). Não foi removida a lógica: segue coberta pelo motor (rationale_names) e pelo caminho MCP de launch/grant. Próximo passo: achar o despacho correto de perms.rs e testar a intrínseca diretamente.

6. Decisões que dependem do usuário

  1. offline-device (F): resolvido pelo usuário em 2026-11-05 — mapeado para PROVISIONING_ALLOW_OFFLINE com a ressalva da §4. Se houver uma action de device feature oficial, substituir a linha da §4.
  2. revokeWhenRequested, instant, softRestriction (B): resolvido pelo usuário (autonomia para pesquisar e implementar com base em fonte oficial). Resultado da pesquisa na §3. 2a. softRestriction (B), forma fraca: resolvido por pesquisa (autonomia do usuário, 2026-11-07). Fonte da regra: AOSP SoftRestrictedPermissionPolicy.java (regras só para READ/WRITE_EXTERNAL_STORAGE; demais = concessão plena). Forma fraca: READ sem allowlist e target < 29 = só coleções de mídia visual/áudio (doc oficial de READ_EXTERNAL_STORAGE); WRITE sem allowlist e target < 29 = sem acesso (grant recusado). Efeito: apps com target < 29 que pedem storage deixam de receber a forma completa pelo runtime sem allowlist. Mudança registrada no PR de 2a. 2e. ACCESS_BACKGROUND_LOCATION: flag corrigida para hardRestricted (decisão do usuário, 2026-11-08). A doc oficial de Manifest.permission (API 29) diz “hard restricted permission which cannot be held by an app until the installer on record allowlists the permission”. Efeito: grant() recusa a permissão sem allowlist do instalador (allow_hard_restricted). Não alterado nesta rodada: a concessão implícita por split para targetSdk < 29 (apply_implicit) segue como antes; a fonte AOSP para esse caminho não foi verificada. 2b. revokeWhenRequested (B): ciclo de update de pacote — aprovado pelo usuário (2026-11-07) e implementado. Gatilho: install do agente com pacote já instalado chama PermissionEngine::update (antes recriava o motor e zerava as permissões). Escopo: splits de platform.xml (exceto BODY_SENSORS → health.*, que depende de feature flag). Para targetSdk < 23 a implícita concedida é aplicada na instalação (modelagem nossa, o AOSP concede na instalação; explícitas pré-M seguem RuntimePending). Efeito colateral aceito: apps com target < 33 que pedem WRITE/READ ganham entradas READ_MEDIA_* no estado. 2c. instant (B): estado de app instantâneo — aprovado pelo usuário (2026-11-07) e implementado. Modelo: opt-in na instalação (install com instant: true), que é o equivalente de adb install --instant. Apps instalados sem a opção não mudam (isInstantApp segue false para eles). Fonte da lista de permissões com instant: core/res/AndroidManifest.xml do AOSP main (28 entradas; 26 existem na tabela, faltam INSTANT_APP_FOREGROUND_SERVICE e FOREGROUND_SERVICE_FILE_MANAGEMENT, lacuna de dado registrada). O modo não muda em update (erro INSTANT_MODE_CHANGE). Não modelado: o cache de instalação instantânea e o PackageInstaller de app instantâneo. 2d.
