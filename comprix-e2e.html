Comprix v1.6.0 end-to-end via MCP: status, latency, and blockers

This document covers running Comprix v1.6.0 (br.com.comprix, x86_64) end to end, driven entirely through rd mcp.

  • App: Jetpack Compose, Room, androidx.startup, ML Kit OCR and barcode.
  • Target: minSdk 26, target 35, a single DEX.
  • Harness: mcp_run.py, which sends JSON-RPC over stdio and times each call from request write to parsed response with a monotonic clock.

Status

Round 2 (current): launch no longer hangs. It runs the whole startup plus the first Compose composition and returns in 0.28–0.45 s with a typed error. Before round 2 it exceeded the 60 s per-call deadline. The activity still dies before the first frame, so no app screenshot is available yet.

How far the launch gets now:

  1. Application.onCreate, the androidx.startup initializers, and MainActivity.onCreate run, then setContentView(ComposeView).
  2. The window is attached and the Recomposer and coroutine dispatchers run.
  3. AndroidComposeView is created, with its accessibility, autofill, content-capture, ViewConfiguration, text-input and focus owners.
  4. The Room database is built: ComprixDatabase_Impl is found by reflection, the InvalidationTracker is set up with locks, and the SQLiteOpenHelper is configured.
  5. The first composition of the app UI runs: Scaffold/Surface, java.time date formatting, and Material vector icons parsed from binary XML (painterResource) and tinted with a BlendModeColorFilter.
  6. The side effects run: WindowInsetsController system-bar appearance and the permission-result callback.
  7. The Room open helper is constructed as DEX:
    • process lock: File, FileOutputStream, FileChannel.lock;
    • getWritableDatabase;
    • Room’s onCreate, which creates the schema.
  8. It stops here: Room’s first query uses SQLiteDatabase.rawQueryWithFactory with a CursorFactory (SQLiteCursor/SQLiteQuery bind path). The in-memory m8 SQL subset does not model it yet. This is the next work item: a SQLite engine able to run Room’s generated SQL (PRAGMA, sqlite_master, INSERT OR REPLACE, bound statements).

Round-2 launch progress chain. Each item is a failure found and fixed in general form:

CAS identity → addAll → getHandler → getResources → Canvas → AccessibilityDelegate → AccessibilityManager → SparseLongArray → Autofill → VibratorManager → TreeSet(Comparator) → ViewConfiguration → CursorAnchorInfo$Builder → DEX TreeSet subclass contains → AutofillCallback → JDK interface closure (Set→Collection CCE) → content capture → Object[] ArrayStore → ClassLoader.loadClass → Method.getAnnotations → ActivityManager.isLowRamDevice → Class.getPackage → ReentrantLock → host ListIterator via the Iterator mref → DateTimeFormatter → Resources.getXml → Xml.asAttributeSet → BlendModeColorFilter → Window.getInsetsController → host panic in permission delivery → Activity.onRequestPermissionsResult → SQLiteOpenHelper.setWriteAheadLoggingEnabled → Class.getAnnotation → NPE (diagnosed with the new guest-stack trace: the m8 SQLiteOpenHelper hook swallowed the DEX subclass’s own constructor) → Context.getCacheDir → ReentrantLock→Lock check-cast → FileOutputStream/FileChannel.lock → (open) rawQueryWithFactory.

Round 1 (history).

  • Blocker 1: the Dex::find_class linear scan, now an O(1) index.
  • Blocker 2: the runBlocking spin, resolved in round 2 by the CAS identity and collection fixes.

What to improve, from these measurements

  1. launch has no wall-clock or fuel bound that covers host loops.
    • A single MCP call can block the server forever.
    • Add a wall-clock watchdog to launch, tap and the other tools that run app code (for example RD_MCP_MAX_CALL_MS). On expiry, return a structured VM_TIMEOUT with the guest stack.
  2. MCP errors carry no guest stack. The CLI --trace stack was what located every root cause in this run. Add a trace argument to launch.
  3. runtime_health should report threads, the pending Looper queue, and frames pumped, so a stalled launch can be diagnosed from MCP alone.
  4. Unmodelled host static fields silently read as null or 0, which hides root causes. boxes and android_build mitigate this.
  5. Traces carry no dex pc.
  6. The session tools are fast: install takes about 15 ms and the metadata tools under 1 ms. The cost is concentrated in launch.
  7. Post-mortem inspection. After a launch crash, every interactive tool (screenshot, ui_tree, widgets, accessibility, get_coverage, native_state) returns NOT_RUNNING. Keeping the dead activity’s last frame, view tree and coverage readable would make crash triage possible from MCP alone.
  8. Host-raised exceptions need guest frames.
    • Guest-constructed Throwables now record the guest stack under --trace; the uncaught-exception log prints it.
    • An NPE raised by the interpreter on a null dereference, once caught and rethrown by guest code, still has no frames. That is exactly the current blocker.
  9. Throwable toString without a message prints Class@id. This happens for some host-materialized exceptions; AOSP prints the class name.
  10. Error messages should name both declarer and receiver. The ListIterator.hasNext failure was really an Iterator.hasNext mref on a host ListIterator. NOT_FOUND should print both the resolved declarer and the receiver class.
  11. launch latency is now dominated by guest work, not the VM: about 0.3–0.45 s for roughly 2,200 distinct DEX methods. install is 22–32 ms with the larger round-2 classpath, and get_api_usage is 66 ms (a full DEX scan, worth caching per install).

Documented deviations

  • Regex: backreferences and lookaround raise PatternSyntaxException (the engine is the Rust regex crate).
  • String.format: a subset of conversions is supported.
  • Reflection:
    • lookup resolves signatures from the dex method_ids, so it covers app-defined methods and referenced platform APIs;
    • getMethods()/getDeclaredMethods() enumeration is not provided;
    • access checks are not enforced.
  • Throwables: no guest stack frames are captured. getStackTrace() returns the last setStackTrace value, else an empty array.
  • Collections.newSetFromMap: returns an independent set rather than a view backed by the map. This is equivalent for the usual idiom, which passes an empty, freshly created map.
  • IdentityHashMap: compares DEX objects by identity but strings and boxes by value.
  • Character classification: approximated with Rust Unicode tables.
  • Collections: subList returns a copy; host ListIterators iterate a snapshot; TreeMap/TreeSet views are snapshots.
  • Resources: themes are not resolved, so ?attr references in XML are reported as absent; default styles are ignored. TypedArray getValue reports ints as colors when the attribute name contains “color” or “tint”. getBaseContext returns the receiver.
  • Device: moto-e5, 720×1440 at 280 dpi, locale en-US (RD_LOCALE overrides). ActivityManager models a 2 GB, non-low-RAM device. ViewConfiguration uses AOSP 14 constants.
  • Graphics:
    • not implemented: shaders, mask filters, blend modes, shadows, and applying color filters (they are recorded only);
    • clips are rectangular and Path.op is approximate;
    • Bitmaps are display lists, with no text shaping or bidi;
    • the draw pass paints DEX views only.
  • Platform services: base classes return defaults. Accessibility reports no services; Autofill and content capture are absent (null). Vibrator calls are logged as I/RdVibrator, insets calls as I/RdInsets. Services are per-class singletons; value builders are inert.
  • Reflection: Classes, Methods and Constructors expose no runtime-visible annotations. There is a single app ClassLoader, whose parent is null.
  • Locks: hold counters under cooperative green threads. Holding a lock across a park does not block other threads; Condition.await returns as a spurious wakeup.
  • java.time: the device zone is UTC. The current time is the deterministic virtual wall clock (RD_EPOCH_MS). Pattern letters supported: y M d H h m s S a E and quotes.
  • SQLite: real SQLite in a child process (ADR 005). The in-memory SQL subset remains as a fallback.
  • Filesystem: virtual and in memory per VM; the host disk is never touched. File locks always succeed (single process); FileChannel.map is unsupported.
  • Unsupported: ML Kit OCR and barcode, which need pthread_create and direct ByteBuffers (accepted M9 limitations).

Open items and what to improve next

  1. Garbage collector. RustyDroid never frees memory. A long session (create a list, then all tabs, about 18 s of virtual time) reaches the 256 MB heap ceiling. A collector that runs at safe points between looper messages (roots: statics, host objects, looper queue, frame callbacks and side maps) is the top item.
  2. type_text for Compose text fields. Today it only types into host EditTexts; Compose fields need the InputConnection/IME path.
  3. Sheet animation speed. The Material sheet settles about 3× slower in virtual time than on a device (exponential approach; still under investigation).
  4. Scanner tab. It returns to Listas (camera/ML Kit not modelled).
  5. Screenshots. Cache the frame until something is invalidated, and use cheaper PNG encoding (deflate level, or a delta frame).
  6. Faster cold launch. Use a warm start or snapshot.
  7. Make NOT_FOUND catchable, and cache negative method resolution.

Round 6: seeing the app in real time without screenshots

Question from the round: can the agent see the full APK in real time via MCP without screenshots? Before this round, no — ui_tree showed a single opaque AndroidComposeView node and the only way to see Comprix was a ~3 MB screenshot (0.3–1.6 s). Now yes, see mcp-observe.md:

  • observe (text/json): visible texts with bounds, tap targets, icon centres, frame version and diff — derived from the recorded display list, so it works on Compose;
  • tap_text: tap by label; observe: true on action tools;
  • MCP resources rustydroid://screen, screen.txt, screen.png, logs with resources/subscribe → notifications/resources/updated (the live demo got 13 notifications for 13 real screen changes, none for unchanged frames);
  • rd mcp --live 0.0.0.0:7878: a browser page with the RustyDroid-rendered frame, screen text, tap-target overlay and last tool latency (long-poll);
  • screenshot cached per frame version; runtime panics isolated (INTERNAL_PANIC, session survives).

Garbage collector (round 7)

The app heap used to be an arena: nothing was freed until the app exited, so a long session headed for the 256 MB budget (the main risk for the Moto E5 / 2 GB floor). It now has a mark-sweep collector; design in docs/gc.md.

Runtime completion and strict regression (round 8, 2026-10-20)

AI-assisted changes address the runtime blockers before integrating the feature branch. Historical round-6/7 numbers above remain historical, not new-device measurements.

  • Iterator.remove now writes through to mutable lists/sets/map-view backing maps, with next/previous cursor adjustment and IllegalStateException rules. COW/immutable iterators remain unsupported for removal. Traversal is still a deterministic snapshot, not a complete fail-fast/live JDK collection model.
  • WeakHashMap keys are weak (strong values, permanent null keys). Minors retain old dead keys until a major collection.
  • Non-moving generations, remembered old writes, live/suspended frame roots and host-temporary scopes permit collection inside one Java invocation. Adaptive object-slot pressure avoids hitting the slot cap before the byte budget and backs off when pinned live objects cannot be reclaimed.
  • Pattern/Matcher/String regex entry points share fancy-regex 0.13 lookaround and backreferences. Backtracking is bounded at 100,000; exhaustion reports REGEX_RUNTIME, never a false match. Source length (64 KiB), delegated regex size/DFA (1 MiB each) and retained cache (128 patterns) are bounded. This is still a documented Java-regex subset, not a complete replacement for Java.
  • Generic saved View delegate/provider traversal supplies Compose virtual node descriptions. Bounded rectilinear Region operations and wrapper-context delegation support the actual provider path, without obfuscated-class hooks.
  • Optional Cranelift 0.104 integer leaf JIT is implemented and off by default. Warmup threshold 32, cache 8,192 entries, native function cap 256; unsupported code falls back to the interpreter. See ADR 007 for safety and architecture.
  • Fuel remains a lifetime counter, but each MCP tool starts a fresh bounded execution window. This avoids exhausting a healthy session’s entire fuel allowance merely through a long sequence of ordinary actions.
