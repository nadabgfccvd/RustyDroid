Registro de engines — Apêndice G

GERADO por cargo xtask engine-report a partir de data/engines.toml. Escopo: registro/detecção dos 28 itens, não implementação de runtimes.

DEX/ELF não identificam a linguagem de origem. signature é uma heurística de nomes/manifest, não validação binária; candidate é compatibilidade de formato; not_detected não exclui um framework. Um APK híbrido pode ter várias assinaturas. Nenhuma autoriza execução.

Consulta

cargo build -p rd-cli
./target/debug/rd engine list --json
./target/debug/rd engine detect app.apk --json
./target/debug/rd engine check flutter --json # exit 2, NOT_IMPLEMENTED
./target/debug/rd inspect app.apk --json     # campo engines

A tool MCP app_info expõe o mesmo relatório em engines; não há nova tool. O catálogo/relatório funciona no build mínimo, sem features opcionais. --data / RD_DATA_DIR explícitos exigem engines.toml; arquivo ausente, inválido ou schema desconhecido retorna erro tipado, nunca fallback silencioso. Sem override, o catálogo embutido permite distribuir o binário sozinho. MCP usa o catálogo embutido.

Features e dependências

Features LANG selecionam contratos. native-engines habilita adapters reais e limitados de C/C++/Rust, sem baixar engines automaticamente. Os contratos LANG são opt-in; o registro não possui features default. CLI/agente preservam advanced-components como default e native/jit continuam opt-in. Dependências são transitivas e propagadas pelo rd-cli/rd-agent; o catálogo permanece completo em qualquer build. O MCP aceita seleção explícita launch.engine; consulte C/C++/Rust.

Exemplo: cargo build -p rd-cli --no-default-features --features lang-04 seleciona LANG-04 → LANG-02 → LANG-01. O campo feature_enabled confirma seleção, enquanto registry_adapter_status continua NOT_IMPLEMENTED. LANG-08 representa a união Mono/IL2CPP; selecionar o módulo inclui LANG-07. A VM já renderiza um subconjunto Compose Android; a feature native executa ELF/JNI limitados em x86_64/ARM64/ARMv7. native-engines acrescenta os adapters c-ndk, cpp-ndk, rust-ndk sobre essa rota. Não implementa Compose Multiplatform, NDK/Android completo nem bridges WebView. Essas rotas existentes e seus limites estão nos ADRs 004, 006 e 007. runtime_status descreve cobertura existente, não disponibilidade neste build; feature_enabled informa somente os contratos LANG. native/jit são seleções independentes. AVAILABLE_BOUNDED informa existência do adapter, não execução observada. Metadados mantêm execution_claimed=false; o relatório do runtime mede instruções reais.

Regras de detecção e rotas

all exige todas as pistas; any exige pelo menos uma quando não vazio. Regras só usam nomes ZIP canônicos (case-sensitive) e classes/metadados de componentes do manifest. Bibliotecas nativas exigem exatamente lib/<abi>/<arquivo>.so; DEX exige classes.dex ou classesN.dex (N ≥ 2). Nenhum asset/lib é descomprimido, extraído, carregado ou executado.

1 — java

  • Rota existente/futura: rd-vm
  • Runtime: DEX parcial (rd-vm); adaptador do registro ausente
  • Limite: DEX tem suporte parcial, não execução universal de Java.
  • candidate: all=[root-dex]; any=[] — DEX é compartilhado: não identifica a linguagem de origem.

2 — kotlin

  • Rota existente/futura: rd-vm
  • Runtime: DEX parcial (rd-vm); adaptador do registro ausente
  • Limite: Dependências Kotlin não provam que o app foi escrito em Kotlin.
  • candidate: all=[root-dex]; any=[] — DEX é compartilhado: não identifica a linguagem de origem.

3 — kotlin-multiplatform

  • Rota existente/futura: rd-engine-compose-mp
  • Runtime: NOT_IMPLEMENTED
  • Limite: Não é possível distinguir KMP/Compose MP apenas pela presença de DEX.
  • candidate: all=[root-dex]; any=[] — DEX é compartilhado: não identifica a linguagem de origem.
  • candidate: all=[suffix:.klib]; any=[] — klib é pista, não prova render Compose Multiplatform.

4 — jvm-dynamic

  • Rota existente/futura: rd-vm
  • Runtime: DEX parcial (rd-vm); adaptador do registro ausente
  • Limite: invoke-custom/method handles e runtimes dinâmicos não são declarados completos.
  • candidate: all=[root-dex]; any=[] — DEX é compartilhado: não identifica a linguagem de origem.

5 — c-ndk

  • Rota existente/futura: rd-ndk/rd-jni
  • Runtime: ELF/JNI parcial; disponibilidade do adaptador depende da engine/feature
  • Limite: C não pode ser atribuído a uma .so genérica. Adapter c-ndk real e limitado exige native-engines; fonte/compilador auditáveis atribuem o idioma.
  • candidate: all=[native-so]; any=[] — ELF é compartilhado: não identifica a linguagem de origem nem valida ABI/payload.

6 — cpp-ndk

  • Rota existente/futura: rd-ndk/rd-jni
  • Runtime: ELF/JNI parcial; disponibilidade do adaptador depende da engine/feature
  • Limite: Adapter cpp-ndk real e limitado exige native-engines. O APK de prova compila C++20 com std::array e sem libc++_shared; não implementa exceções nem STL/NDK completos.
  • candidate: all=[native-so]; any=[] — ELF é compartilhado: não identifica a linguagem de origem nem valida ABI/payload.

7 — rust-ndk

  • Rota existente/futura: rd-ndk/rd-jni
  • Runtime: ELF/JNI parcial; disponibilidade do adaptador depende da engine/feature
  • Limite: Nome .so e símbolos removidos não provam Rust. Adapter rust-ndk real com native-engines, validado por APK Android no_std source-built; não implica std/async.
  • candidate: all=[native-so]; any=[] — ELF é compartilhado: não identifica a linguagem de origem nem valida ABI/payload.

8 — go-mobile

  • Rota existente/futura: rd-engine-gomobile
  • Runtime: NOT_IMPLEMENTED
  • Limite: Marcador gojni é uma assinatura heurística, não análise de símbolos.
  • candidate: all=[native-so]; any=[] — ELF é compartilhado: não identifica a linguagem de origem nem valida ABI/payload.
  • signature: all=[native:libgojni.so]; any=[] — Marcador de bind gomobile.

  • Runtime: ELF/JNI parcial; disponibilidade do adaptador depende da engine/feature
  • Limite: Somente a rota ELF/JNI é parcial; runtime Objective-C não é implementado. Uma .so genérica só produz candidato.
  • candidate: all=[native-so]; any=[] — ELF é compartilhado: não identifica a linguagem de origem nem valida ABI/payload.

Contrato e erros

EngineAdapter define parse(Artifact) -> Process, event(process, event) e syscall(process, call). Os 28 adaptadores do registro são indisponíveis: toda operação retorna {code, cause, suggestion, module_id} com code: NOT_IMPLEMENTED e module_id: LANG-xx. Nenhum processo fictício é retornado, mesmo com --all-features. A cobertura DEX existente pertence a rd-vm, pelas rotas rd vm/rd app, não a estes adaptadores.

CódigoSituação
NOT_IMPLEMENTEDOperação de runtime/contrato ainda ausente (CLI exit 2)
UNKNOWN_ENGINEID não registrado (exit 1)
INVALID_ENGINE_CATALOGSchema, IDs, módulos, ciclos, regras ou status inválidos
CATALOG_TOO_LARGECatálogo maior que 1 MiB
DETECTION_LIMITMais de 100.000 entradas ZIP
IO_ERRORArquivo de catálogo/APK inacessível

Ao exceder o limite de entradas, rd engine detect continua falhando com DETECTION_LIMIT. inspect --json e MCP app_info preservam os dados básicos; engines contém analysis_status: not_analyzed e error tipado, não uma lista vazia que fingiria ausência de assinaturas. Catálogo explícito inválido continua sendo erro, nunca fallback silencioso.

Diagnósticos do relatório: DUPLICATE_ZIP_ENTRY, NON_CANONICAL_ARTIFACT_PATH, UNKNOWN_ABI, AMBIGUOUS_SOURCE_LANGUAGE. Nomes duplicados contam uma vez. Evidências/diagnósticos contêm no máximo 4 amostras por predicado/diagnóstico, mantendo a contagem total. Todos os 28 IDs aparecem, inclusive not_detected; ordem e amostras são determinísticas. execution_claimed: false e artifact_validation: not-performed são contratos explícitos.

Testes e definição de conclusão

  • tests/engines/signatures.json: exatamente 28 casos golden de DETECÇÃO, um por ID. Fixtures APK/AXML/ZIP são geradas em memória; nenhum binário é commitado. Testes cobrem híbridos, pistas incompletas, ambiguidades, paths hostis, duplicatas, teto de entradas e amostragem.
  • Tests de contrato exercitam parse/event/syscall para os 28 itens: sempre erro tipado. Builds mínimo, features individuais e todas são independentes.
  • cargo xtask engine-report regenera este arquivo; cargo xtask engine-spec regenera apenas a tabela marcada no Apêndice G; cargo xtask compat-report atualiza o placar oficial. Testes barram drift.
  • Integração OSS explícita: baixe um APK com golden-apks/fetch.sh e rode RD_TEST_APK=/caminho/app.apk cargo test -p rd-engine-registry --test registry real_oss_apk_inventory -- --ignored. Sem a variável/arquivo, o teste falha; não há falso sucesso por pular a fixture. No teste normal ele é ignored.

Registro/detecção concluídos ≠ runtime concluído. Uma engine só pode mudar de NOT_IMPLEMENTED após crate/adaptador real feature-gated, ADR, parse/event/syscall funcionais, golden flow com APK OSS e gate Moto E5. As capacidades parciais de M9 já existentes não equivalem às engines de M11. Veja ADR 003 e ROADMAP.
